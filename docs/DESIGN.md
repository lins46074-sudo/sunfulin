## 1. 模块划分

```
                      config.py
                  （唯一配置出口）
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
    prompts.py        store.py        （参数）
  提示词集中管理    向量库访问层
                         │
                         ▼
                     ingest.py          建库：读 → 切 → 向量化 → 存
                         │
                         ▼
                      rag.py            检索工具 + Agent 组装
                    ╱       ╲
                   ▼         ▼
              chat.py     web.py
             命令行端     Streamlit 端
```

划分原则是**按变更原因分层**，而不是按技术组件分层：

- 改提示词 → 只动 `prompts.py`
- 换向量模型 / 换数据库 → 只动 `store.py`
- 调切片参数 → 只动 `config.py`
- 改交互 → 只动 `chat.py` 或 `web.py`

`rag.py` 是双端唯一的共享入口，命令行和网页都通过它构建 Agent。
这保证了两种交互方式的行为绝对一致——不会出现「网页版能溯源、命令行版不能」这种偏差。

## 2. 关键设计决策

### 2.1 用 Agent 而不是固定 RAG 链

| | 固定链 | 本项目的 Agent 方案 |
|---|---|---|
| 检索时机 | 每次提问都检索 | 模型自己判断，常识问题不检索 |
| 召回不足 | 只能硬答或拒答 | 可改写关键词二次检索 |
| 开销 | 单次模型调用 | 多一次决策调用 |

选 Agent 是因为**准确率优先于延迟**：这是问答工具，答错的代价远大于多等一秒。
另外固定链在「你好」这类提问上会白白消耗一次向量检索，
还可能把不相关片段塞进上下文，反而干扰模型。

### 2.2 检索工具返回格式化文本，而不是 Document 对象

这是整个项目里最关键的一个决定。

```python
# 做法：在工具内部就把编号和来源拼进字符串
parts.append(f"[{idx}] 来源：{source}\n{doc.page_content}")
```

如果直接把 `Document` 列表丢回给模型，来源信息是**元数据**，
模型需要在生成时自己把片段和来源对应起来——这本质上又变成了一件「求模型做对」的事。

而把编号拼进文本后，来源标注变成了模型**照着念**的事：
它看到的就是 `[1] 来源：price.md`，输出 `【1】` 几乎是必然的。
**能用数据结构保证的，不要交给提示词。**

### 2.3 中文标点优先的切片策略

默认分隔符 `["\n\n", "\n", " ", ""]` 对中文只有换行和空格有效。
中文段落常常一整段没有换行，超过 `chunk_size` 后会被硬切：

```
...这是第59句用来测试中文切分逻辑的示 | 例文本内容。这是第60句...
                  ↑ 句子被拦腰截断，两个片段的语义都不完整
```

改用 `["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""]` 后，
切分点优先落在段落、句末标点处。

**代价**：切片长度不再均匀（实测 1431 字切成 494 / 480 / 480 / 121 四块），
最大块接近上限、最小块可能很短。但对检索来说，**语义完整比长度均匀重要得多**。

这一点由 `tests/test_rag.py` 中的回归测试守住，
并且测试本身用默认分隔符做对照组，确认断言真的能抓到截断问题（而非空跑）。

### 2.4 配置集中且全部外置

所有可调项都在 `config.py` 里读环境变量，代码中不出现魔法数字：

```python
TOP_K = int(os.getenv("RAG_TOP_K", "4"))
```

好处是**换模型端点不需要改代码**。项目默认走 DeepSeek 的 Anthropic 兼容端点，
换成官方 Claude 只要改两行配置：

```ini
ANTHROPIC_BASE_URL=https://api.anthropic.com
RAG_MODEL=claude-opus-5
```

这也是选 `langchain-anthropic` 而非 OpenAI 系 SDK 的原因——
Anthropic Messages API 已成事实标准，DeepSeek、月之暗面等国内厂商都提供了兼容端点，
一套代码可以横跳。

### 2.5 两个容易踩的坑（已在代码中处理并注释）

**其一：`HF_ENDPOINT` 必须在导入 `langchain_huggingface` 之前设置。**

`huggingface_hub` 在**被导入时**就读取并缓存镜像地址，
晚于它设置环境变量不会生效，表现为模型下载静默卡死。
所以 `store.py` 的第一行是 `import config`，并附了注释说明原因。

**其二：Windows 控制台默认 GBK 编码。**

打印文档片段时遇到 GBK 无法表示的字符会抛 `UnicodeEncodeError` 直接崩溃。
`config.py` 在导入时把标准输出强制切到 UTF-8。

## 3. 幻觉抑制的三层设计

```
第 1 层  数据链路   工具返回带编号的格式化文本
        （最可靠）  来源由代码拼接，模型只能照着用

第 2 层  提示词     只依据检索内容作答 / 必须标注来源
        （较强）    / 查不到时回复固定话术

第 3 层  交互兜底   Web 端可展开查看本轮检索到的原始片段
        （人工核查）用户能自己验证答案依据
```

设计时按**可靠性递减**排序，把最强的保证放在最前面。
仅靠提示词（第 2 层）是不够的——实测中模型在召回内容不相关时，
仍会拿常识凑一个看起来合理的答案。

关键是给「查不到」设计一个**模型愿意使用的出口**：
`【知识库没有找到相关内容】` 这个固定话术足够明确，
模型不需要自己组织语言，拒答的意愿显著提高。

需要如实说明：这套约束**能显著降低幻觉，但不是 100% 可靠**。

## 4. 已知局限与改进方向

按优先级排列：

| 局限 | 影响 | 改进方向 |
|---|---|---|
| 无量化评估 | 参数调优靠经验，无法证明改动是否真的变好 | 建标注集 → Hit Rate / MRR 评估检索 → Ragas 评估生成 |
| 全量重建索引 | 文档多时建库慢 | 按文件哈希做增量索引 |
| 会话状态在内存 | 进程重启后对话历史丢失 | 换 `SqliteSaver` / Redis Checkpointer |
| 纯向量检索 | 专有名词、型号等关键词召回弱 | 引入 BM25 做混合检索 + Rerank |
| 单机部署 | 多用户时向量模型在每个进程重复加载 | 检索能力拆为独立服务，模型常驻 |

这些不是「没想到」，而是**在当前规模下不值得做**。
个人与团队级文档（几十到几千份）用现在的方案完全够用，
过早引入分布式检索反而是负担。

## 5. 测试策略

`tests/test_rag.py` 的 21 个用例遵循一条原则：
**不依赖 API 凭证，也不依赖已建好的向量库**，因此在 CI 和无网络环境下都能跑。

覆盖重点放在**容易静默出错的逻辑**上，而不是追求行数覆盖率：

- 切片是否真的没截断句子（含默认分隔符对照组）
- 来源元数据是否跟着切片走（丢了就无法标注出处）
- 工具输出格式是否包含编号与来源名（模型能否标注引用全靠它）
- 检索条数是否真的走配置（而非硬编码）
- 内容解析能否容忍多种返回结构

外部依赖（向量检索）用 `monkeypatch` 替换，测的是**格式化与流转逻辑**，
不测 Chroma 本身——那是第三方库的责任。
